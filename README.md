### **4. Проблемы монолитного решения**

- **Высокий риск ошибок**: из-за высокой связанности между модулями возрастают вероятность человеческих ошибок и деградаций в соседних модулях. Это усиливается отсутствием unit и интеграционных тестов.
- **Усложнена разработка**: попытки рефакторинга более чем одним разработчиком неизбежно приведут к предыдущей проблеме и помножатся на конфликты в изменениях кода.
- **Усложнено масштабирование системы**: обращение к внешнему API и обращение к базе данных происходит синхронным образом, что мешает масштабированию системы. Например, увеличение количества клиентских запросов может привести к спаму внешнего API и слабо предсказуемому времени ответа пользователю, что не желательно.
- **Усложнено масштабирование системы**: в текущем виде единственный способ - запустить приложение в нескольких копиях и накрыть балансировщиком нагрузки (не представлен).
- **Нет аутентификации**
  - нет аутентификации (не представлена в репозитории): приложение не знает, какие пользователи существуют и не может идентифицировать их
  - нет авторизации: обработчики в [handlers/sensors.go](apps/smart_home/handlers/sensors.go) не проверяют, какой пользователь делает запрос и имеет ли права на выполнение операций
  - как следствие нет разделения на техника (кто устанавливает пол) и пользователя (кто смотрит на датчики)
- **Никак не продумано добавление устройства**
  - CreateSensor просто добавляет сенсор в базу данных, но не проверяет, существует ли уже сенсор с таким идентификатором и наш ли это сенсор вообще.
    - В случае наличия конкурентов с совместимым API/производителем/прошивкой у сенсора можно подключить сторонний сенсор без нашего ведома.
  - В идеальном случае нам нужно точно знать, какие сенсоры мы продали и добавлять только их, причём идентифицируя каждый.
    - Таким образом клиенты смогут подключить только те сенсоры, за которые бизнес явно получил деньги
    - Знание о том, какой где был продан и когда был подключен также поможет отделу продаж в поиске новых клиентов/рынков и планировать развитие.


  - Открыть в браузере [web-интерфейс PlantUML-сервера](http://localhost:8888/)
  - Скопировать содержимое файла в буфер обмена
  - Вставить содержимое буфера обмена в поле слева на web-интерфейсе

# Задание 4. Создание и документирование API

### 1. Тип API

#### Взаимодействие с UI

Для взаимодействия с мобильным приложением и web-интерфейсом логичнее использовать REST API.
Основные преимущества такого подхода заключаются в следующем:
- **Общепринятый стандарт**: REST API является стандартом, который широко используется в современном программировании. Это означает, что большинство разработчиков знают его и могут легко понять и использовать его. Будет очень легко нанять разработчиков, которые уже знакомы с REST API. Многие языки программирования имеют готовые фреймворки для работы с REST API, это позволяет разрабатывать разнообразные приложения, используя один и тот же API. В нашем случае это мобильное приложение и web-портал.
- **Открытая документация**: благодаря openapi/swagger, API легко документируется. В качестве примера можно посмотреть на [temperature-api](docs/diagrams/api/temperature-api.yaml). Этот файл может быть открыт с помощью OpenAPI UI и методы из него вызваны в удолном интерфейсе. Точно такой же интерфейс автоматически добавляется в REST API приложения, если использовать фреймворк. Примером может послужить [temperature-api](apps/temperature-api/main.py). 
- **Простота отладки**: REST API легко отладить и тестировать. Текстовый протокол не самый экономичный, как и формат JSON, но он легко форматируется в человекочитаемый вид и потому быстро воспринимается людьми без дополнительных инструментов.

#### Взаимодействие с устройствами

Это более сложный вопрос и в тестовом задании я намеренно не хотел бы указывать каукю-то конкретику. В моей текущей работе встречаются самые разнообразные устройства, как работающие по JSON/XML/TXT с тривиальными сообщениями, так и работающие по более сложным протоколам RTSP/SRTP/ONVIF/SSDP с проприетарными дополнениями в них. Поэтому в моём решении намеренно (см. [Диаграмма агрегатора данных с устройств](docs/diagrams/component/to-be_aggregator.puml) ) для разных производителей предполагается написать отдельный шлюз, который работает по их протоколу (потенциально подгружая сторонние проприетарные модули, которые мы совершенно точно не хотим загружать в память основного приложения из соображений безопасности и стабильности). Подразумевается, что каждый шлюз будет работать обособленно, в отдельном docker (если нужно - VM) контейнере.

#### Взаимодействие внутри системы

У фирмы ООО «Тёплый дом» очень мало сотрудников. На 5 разработчиков уже дополнением кладутся роли руководителя и DevOps/SRE, поэтому собственные решения нужно сократить до минимума. В качестве шин данных, кешей ключ-значение и т.д. предлагаю использовать готовые решения, запускаемые не сложнее `docker run ...`. Обмен данными с этими инструментами самостоятельно проектировать не потребуется, так как они уже есть в стандартной библиотеке множества языков. В подавляющем большинстве случаев работа ведётся по принципу pub/sub (издатель-подписчик).

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

Ревьюер будет проверять точно так же.
